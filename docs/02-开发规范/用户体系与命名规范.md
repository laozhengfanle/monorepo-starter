# 用户体系与命名规范（fork 必读）

> **本文档是 fork 本项目后扩展任何"人"相关功能的唯一权威指南。**
> 无论你要做商城会员、代理商、员工、租户、还是新的后台角色——先读本文档，再动手。
>
> 核心理念：**身份底座统一，业务档案分端**。账号（Account）是唯一的身份容器，
> 登录/凭证/令牌/审计全部复用；各端（admin/member/agent/staff…）通过 `userType`
> 区分，各自持有独立档案表与业务模块，**互不侵入**。

---

## 1. 术语铁律（最高优先级，所有 AI 代理必须遵守）

### 1.1 禁止使用 `user`

**除 §1.3 的显式例外外，禁止在代码、数据库、接口、文档、注释、分支名、commit message 中使用 `user` 指代"某类用户"。**

原因：`user` 是语义黑洞——它同时被用来指"管理员""会员""代理商""员工"，导致：

- 读代码者无法判断一段逻辑到底服务谁；
- 多端并存时，`user` 极易被错误复用（典型事故：会员逻辑与管理端逻辑互相复用了对方的档案表，两套身份体系割裂）；
- 全局搜索 `user` 会命中大量无关内容（`user-agent`、`userType`、`useUser`…），定位成本极高。

### 1.2 标准术语表（只能使用这些词）

| 术语         | 含义                                                                                                   | 允许位置   |
| ------------ | ------------------------------------------------------------------------------------------------------ | ---------- |
| **account**  | 身份容器（`Account` 表）。**唯一**承载凭证/令牌/启停/版本号的实体                                      | 全栈       |
| **identity** | 登录标识（`AccountIdentity`：username/phone/email/oauth 多方式登录同一 account）                       | 全栈       |
| **member**   | C 端会员（`userType='member'`）。商城/电商/用户端业务                                                  | 全栈       |
| **admin**    | 后台管理员（`userType='admin'`）。管理端业务，已有 `AdminProfile` + RBAC                               | 全栈       |
| **agent**    | 代理商/分销商（`userType='agent'`）。分销/代理业务                                                     | 全栈       |
| **staff**    | 员工/内部成员（`userType='staff'`）。内部协作业务；如需区分叫 `employee`，团队自定但**必须全文一致**   | 全栈       |
| **profile**  | 某端的业务档案（`AdminProfile`/`MemberProfile`/`AgentProfile`/`StaffProfile`）。只存业务数据，不存凭证 | 全栈       |
| **party**    | 万不得已需要"所有类型的账户/自然人"统称时的词（比 `user` 准确）                                        | 仅泛称场景 |

### 1.3 允许使用 `user` 的例外（穷举，不得扩展）

1. **`User-Agent` / `userAgent`**：HTTP 标准头，指浏览器/客户端代理，与"用户实体"无关（如 `AuditLog.userAgent`）。
2. **指代"全部类型的账户"且无法用 `party`/`account` 替代的泛称场景**——但**优先用 `account`**。函数/文件命名时若真的代表全体（如 `resolveAccountPermissions` 处理 admin+member 共用逻辑），可用 `account*` 表达，不要用 `user*`。
3. **存量代码迁移期**：现有 `userType` 字段、`AuthUser` 类型等在完成迁移（见 §7）前保留，但**新代码一律不得新增** `user` 命名。

### 1.4 落地检查清单（写代码前自问）

- [ ] 这个实体是"人"吗？→ 用 `account` 或具体端名（member/admin/agent/staff）
- [ ] 这个字段/文件/方法服务哪一端？→ 用端名前缀（`memberId`、`MemberProfile`、`agentModule`）
- [ ] 我在写"全体"？→ 用 `account*`，不要用 `user*`
- [ ] 我引用的是浏览器 UA？→ 允许 `userAgent`

## 2. 体系架构：身份底座统一，业务档案分端

```
                        ┌─────────────────────────────────────────┐
                        │            Account（身份容器）            │
                        │  id · userType · enabled · tokenVersion  │
                        │  lastLoginAt · deletedAt                  │
                        └──────────────┬──────────────────────────┘
                                       │ 1:N
                    ┌──────────────────┴──────────────────┐
                    │          AccountIdentity             │
                    │  username / phone / email / oauth    │
                    │  （多方式登录同一账户）                │
                    └─────────────────────────────────────┘

  userType='admin'   userType='member'   userType='agent'   userType='staff'
        │                 │                  │                  │
  AdminProfile       MemberProfile      AgentProfile       StaffProfile
  AdminRole/RBAC     （商城会员档案）     （分销/代理档案）    （内部员工档案）
  AdminMenu          MemberModule       AgentModule         StaffModule
  权限点体系          会员业务表          代理业务表           员工业务表
```

**要点：**

1. **凭证与令牌只在 Account/AccountIdentity 层**：登录锁定、JWT 双 token、tokenVersion 撤销、jti 黑名单、审计——所有端**复用同一套**（`auth` 模块），新端零改造。
2. **各端档案表互不引用**：`AdminProfile` 不碰会员字段，`MemberProfile` 不碰管理端。跨端权限判定走 `resolveAccountPermissions`（admin 用）或各端自己的判定逻辑。
3. **认证接口按端分离**：`POST /auth/member/login`（或各端自己的 AuthController），不要把所有端塞进一个 `login` 端点——便于独立限流/风控/审计词表。

## 3. `userType` 枚举设计（Account 的端类型开关）

`Account.userType` 是**端类型**（不是"角色"）。角色权限是 admin 端内部概念（AdminRole）；member/agent/staff 端是否有"角色"由该端自己决定。

| 值       | 端       | 档案表                  | 已有设施                  |
| -------- | -------- | ----------------------- | ------------------------- |
| `admin`  | 管理后台 | `AdminProfile`          | ✅ 完整（RBAC/菜单/审计） |
| `member` | C 端会员 | `MemberProfile`（待建） | 底座可复用；业务待建      |
| `agent`  | 代理商   | `AgentProfile`（待建）  | 底座可复用；业务待建      |
| `staff`  | 员工     | `StaffProfile`（待建）  | 底座可复用；业务待建      |

**新增端类型流程**：改 schema 加枚举值 → 新建档案表 + 业务模块 → 新建该端 AuthController/Resolver（复用 TokenIssuanceService/LoginLockService/AuditService）→ 字典 `account_type` 同步 → 按 §5 规范落地。**禁止**为会员/代理临时改 `AdminProfile` 或复用管理端 RBAC。

## 4. 会员端（member）扩展指南 —— 商城场景标准做法

> 以"fork 后开发商城会员"为例，其他端（agent/staff）流程相同，换名即可。

### 4.1 数据层

```prisma
// 会员档案：只存业务数据，凭证在 Account/AccountIdentity
model MemberProfile {
  id         String   @id @db.Uuid
  accountId  String   @unique @map("account_id") @db.Uuid
  nickname   String   @default("") @db.VarChar(50)
  phone      String   @default("") @db.VarChar(20)
  email      String   @default("") @db.VarChar(100)
  avatar     String   @default("") @db.VarChar(255)
  // 会员特有字段：等级、积分、余额等按业务补充
  createdAt  DateTime @default(now()) @map("created_at") @db.Timestamptz
  updatedAt  DateTime @updatedAt @map("updated_at") @db.Timestamptz

  account Account @relation(fields: [accountId], references: [id], onDelete: Restrict)
  @@map("member_profile")
}
```

- 建 `Account` 行：`userType='member'`；`AccountIdentity` 存手机号/邮箱 + 凭证哈希（bcrypt，沿用现有写法）。
- 商城业务表（订单/购物车/地址等）用 `memberId` 关联 `MemberProfile.accountId`，**不要**建自己的"用户表"。

### 4.2 接口层

- `MemberModule` + `member-auth.controller.ts`：`POST /auth/member/register`、`POST /auth/member/login`、`POST /auth/member/refresh`（**复用** TokenIssuanceService.refresh）、`GET /auth/member/me`。
- 注册是**公开端点**（无 JWT）——必须套安全基线：
  - `@Throttle` 独立限流（如注册 5/min/IP、登录 5/min/IP，对齐现有 auth.controller）；
  - Turnstile 人机验证（启用时校验，沿用 `TurnstileService`）；
  - 手机号/邮箱验证码（验证码走 `NotificationsModule` 的 provider 抽象，生产换真实短信/邮件服务）；
  - 登录锁定复用 `LoginLockService`（按 accountId + IP）。
- 会员鉴权守卫：新建 `MemberJwtGuard`（复制 `JwtAuthGuard` 逻辑并加 `userType==='member'` 校验），**不要**给会员挂 `PermissionGuard`/`AdminProfile` 相关守卫。

### 4.3 禁止事项（红线）

- ❌ 会员登录/注册复用 `POST /auth/login`（那是 admin 端，限流/词表/审计都不匹配）。
- ❌ 会员档案写入 `AdminProfile` 或会员数据引用 `AdminRole`。
- ❌ 新建任何名为 `user`/`User` 的表、字段、接口（见 §1）。
- ❌ 把管理端 `me()` 逻辑照抄给会员——各自实现，共享底座即可。

## 5. 其他端（agent/staff）快速指引

与 §4 会员端完全同构：`AgentProfile`/`StaffProfile` + `AgentModule`/`StaffModule` + `agent-auth`/`staff-auth` 控制器 + 各自档案与业务表。差异仅在业务语义与字典/权限设计。**底座（Account/Identity/token/锁定/审计）零改造。**

## 6. 存量 `user` 命名迁移清单（渐进执行，新代码零增量）

| 现状                                        | 目标                                              | 说明                               |
| ------------------------------------------- | ------------------------------------------------- | ---------------------------------- |
| `Account.userType` / `user_type`            | `accountType` / `account_type`                    | 端类型字段改名（迁移期兼容读取）   |
| `AuthUser` 类型                             | `AuthAccount`                                     | 承载 accountId+userType 的认证主体 |
| `@CurrentUser()` / `current-user.decorator` | `@CurrentAccount()` / `current-account.decorator` | 认证主体注入装饰器                 |
| `req.user`                                  | `req.account`                                     | Guard 挂载的认证主体               |
| 注释/文档中的"用户"泛指                     | 按语境改 `账户`/`会员`/`管理员`                   | 术语铁律                           |

> 迁移不影响运行时行为（纯命名）；涉及 schema 改名需 `db:migrate` 生成迁移。

> 遗留 `model User`（表 `user`）已在本版本彻底删除（schema + 演示数据 + 权限码 + 文档），
> 全库禁止出现 `User` 表/模型；新代码不得新建任何 `user`/`User` 命名（见 §1）。
