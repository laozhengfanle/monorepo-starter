# 权限控制

> 本文介绍基于 RBAC 的权限模型与实现：角色、权限点、账户级覆盖、`PermissionGuard` 用法与新增权限点流程。核心代码在 `apps/server/src/modules/auth/permission.guard.ts`、`account-permission.util.ts`、`permission.decorator.ts`。

## 1. RBAC 模型总览

权限体系由 4 张核心表构成（见 `apps/server/prisma/schema.prisma`）：

| 表                   | 角色          | 说明                                                                           |
| -------------------- | ------------- | ------------------------------------------------------------------------------ |
| `admin_role`         | 角色          | 如 `super_admin`、`operator`，可启停                                           |
| `admin_menu`         | 菜单 / 权限点 | `code` 即权限码（如 `admin:account:list`），`enabled`/`visible` 控制生效与展示 |
| `admin_role_menu`    | 角色-菜单关联 | 角色拥有哪些权限点                                                             |
| `admin_account_menu` | 账户级覆盖    | `type: 'grant'                                                                 | 'deny'`，对单个账户追加或移除权限 |

账户 → 权限的解析链路：

```text
account → adminRoles（admin_account_role）→ roleMenus → menu.code（permissionCode）
        ↘ 叠加 admin_account_menu 账户级覆盖：grant 追加、deny 移除（deny 优先）
```

`me()` 查询与 `PermissionGuard` **共用同一个** `resolveAccountPermissions`，保证前端菜单显示与后端鉴权结果一致。

## 2. PermissionGuard 用法

`PermissionGuard` 读取 `@RequirePermission` 声明的权限点并逐个校验：

```ts
@Resolver(() => AdminAccount)
export class AdminAccountResolver {
  @Query(() => [AdminAccount])
  @UseGuards(JwtAuthGuard, PermissionGuard) // 必须排在 JwtAuthGuard 之后（依赖 request.user）
  @RequirePermission('admin:account:list')
  async accounts() { ... }

  @Mutation(() => AdminAccount)
  @RequirePermission('admin:account:create')
  async createAccount() { ... }
}
```

规则：

- `@RequirePermission(...)` 支持多个权限码，**全部拥有**才放行（AND 语义）；
- 未登录抛 `ForbiddenException('未认证')`；权限不足抛 `ForbiddenException('权限不足')`；
- 未标注 `@RequirePermission` 的接口默认放行（仅需登录），敏感操作请显式声明；
- 守卫会实时查询数据库聚合权限，权限变更**无需重新登录**即可生效（无权限缓存）。

## 3. super_admin 绕过逻辑

当账户拥有 `admin_role.code === 'super_admin'` 的角色时，`PermissionGuard` 直接放行，不看权限点；前端 `me()` 同样返回全量菜单。注意：绕过判断的是**角色编码**，不是菜单权限码，因此 `super_admin` 角色本身不需要挂任何权限点。

## 4. 新增权限点（完整流程）

1. **建权限点记录**：在 `admin_menu` 表新增一行（或通过菜单管理接口），`code` 形如 `模块:资源:动作`，如 `order:order:export`；`type` 为按钮/菜单，`enabled=true`；
2. **挂到角色**：在 `admin_role_menu` 关联需要的角色（或在角色管理界面勾选菜单）；
3. **后端声明**：接口上加 `@RequirePermission('order:order:export')`；
4. **前端收敛**：菜单/按钮显隐用 `me()` 返回的权限集合控制（如 `usePermission('order:order:export')`），按钮禁用优先于隐藏，避免布局跳动；
5. **补测试**：为新的权限分支补 `PermissionGuard` 单测（`super_admin` 绕过、deny 覆盖、权限不足抛错）。

命名建议：`{领域}:{实体}:{动作}`（`list/create/update/delete/export/...`），避免动作混在实体里。

## 5. 账户级覆盖（grant / deny）

`admin_account_menu` 用于"给某人单独开/关某个权限点"而不动角色：

```ts
// grant：给账户追加一个角色未包含的权限点
{ accountId, menuId, type: 'grant' }
// deny：从账户身上移除角色已包含的权限点（deny 优先于角色权限）
{ accountId, menuId, type: 'deny' }
```

解析顺序（`resolveAccountPermissions`）：角色基线 → grant 追加 → deny 移除。deny 永远优先，覆盖后的集合与 `me()` 返回一致。

## 6. 边界与注意事项

- **越权护栏（角色管理，P1-1 修复）**：非超管操作者
  - 只能**管理自己持有的角色**（`admin_role` 未绑定的角色不可改/删 → `ROLE_MANAGE_FORBIDDEN`）；
  - 授予/更新的权限点必须 **⊆ 自己已持有**（`resolveAccountPermissions` 判定 → `ROLE_PERMISSION_FORBIDDEN`）；
  - 内置 `super_admin` 角色仅超管可管理。超管不受限。
- **超管保护（账户管理，P1-2 修复）**：移除 `super_admin` 角色、禁用/删除超管账户必须由**超管本人**操作（`SUPER_ADMIN_DEMOTE_FORBIDDEN`），且系统至少保留一个启用超管（`SUPER_ADMIN_PROTECTED`）。
- **与限流叠加**：权限校验不替代限流，敏感接口仍需 `@Throttle` 收紧（见《认证与安全.md》）；
- **与审计叠加**：变更类操作（建角色、改权限、分配角色）应同时写审计（`ROLE_ASSIGNED` / `PERMISSION_CHANGED` 等）；
- **模块边界**：权限码是跨前后端的字符串契约，不要拼错——前端与后端引用同一份 `@starter/contracts` 里的类型（如有）或保持注释一致；
- **性能**：每次请求实时查库聚合权限，权限链路深时可考虑按账户做短 TTL 缓存（当前实现刻意不缓存以保证即时生效）。
