# 07 故障排查

> 按"症状 → 原因 → 解决"组织，覆盖开发与部署中最常遇到的问题。先跑一遍诊断命令再对症下药。

---

## 1. 端口占用（EADDRINUSE / 页面打不开）

**症状**：`pnpm exec nx serve server` 报 `EADDRINUSE` / `Error: listen EADDRINUSE: address already in use :::3301`；或 3302 打开的不是本项目页面。

**排查**：

```bash
lsof -i :3301        # macOS / Linux
netstat -ano | findstr 3301   # Windows
```

**解决**：杀掉占用进程，或改端口（见《04-配置参考.md》第 4 节）：

```bash
kill -9 <PID>
```

> 3302 打不开也可能是代理残留：确认 `nx serve admin` 是唯一在跑的前端进程。

---

## 2. 数据库连接失败

**症状**：`prisma migrate dev` / 启动 server 报 `Can't reach database server`、`Connection refused`、`password authentication failed`、或 `环境变量校验失败: DATABASE_URL: ...`。

**排查顺序**：① `apps/server/.env` 是否存在、`DATABASE_URL` 是否与本机一致；② 服务是否在跑：`pg_isready`（本机 PG）或 `docker ps`；③ 数据库是否存在：`docker compose up -d postgres` 首次启动会自动建 `monorepo_starter` 库（`POSTGRES_DB`）。

**解决**：

```bash
# 没装 PG 时用 Docker
docker compose up -d postgres
# 确认连接串（默认模板）
# DATABASE_URL=postgresql://postgres:postgres@localhost:5432/monorepo_starter?schema=public
```

> 连的是 Docker 的 PG 而模板连的是 localhost？容器端口映射 `127.0.0.1:5432:5432`，本机 localhost 即可，无需改。

## 3. GraphQL schema 不更新

**症状**：改了 Resolver 的 `@ObjectType` / `@Query`，但前端 codegen 出来的类型没有新字段 / Apollo Sandbox 里看不到新 query。

**原因**：`graphql/schema.gql` 是**生成物**，在 server **启动时**由 Code-First 自动生成（`autoSchemaFile: graphql/schema.gql`）。

**解决**：重启 server（`nx serve server` 是热重载，会重新生成），确认 `git status` 里 `graphql/schema.gql` 有新内容后再跑前端 codegen：

```bash
pnpm exec nx run @starter/admin:generate-graphql
```

> 如果 schema.gql 没变化：检查新模块是否在 `app.module.ts` 注册、Resolver 是否被 `@Resolver()` 标注。

---

## 4. orval 生成的 client 过期（REST 场景）

**症状**：前端调 REST 接口报类型错误 / 缺方法，而后端 DTO 明明已经改了。

**原因**：`packages/shared/api-client/src/generated/` 是从 `openapi/openapi.json` 生成的，**不会自动同步**。

**解决**（契约变更流程，根 README 也有声明）：

```bash
pnpm exec nx run server:generate-openapi   # 1) 后端重新发射 OpenAPI → openapi/openapi.json
pnpm generate:api                          # 2) orval 重新生成前端 client
```

> 提交时记得把 `openapi/openapi.json` 与 `packages/shared/api-client/src/generated/` 一起提交（生成物入库）。

## 5. pnpm install / pnpm add 报 catalog 错误

**症状**：

- `pnpm add <包>` 报 `<包> is not in the catalog` / "not allowed"；
- CI 里 `pnpm install --frozen-lockfile` 失败。

**原因**：`pnpm-workspace.yaml` 开启了 `catalogMode: strict`，**只允许安装 catalog 里登记过的依赖**。

**解决**：

1. 打开 `pnpm-workspace.yaml`，在 `catalog:` 段新增版本条目：
   ```yaml
   catalog:
     <包名>: ^版本范围
   ```
2. 目标包的 `package.json` 用 `"<包名>": "catalog:"` 引用；
3. `pnpm install` 更新 lockfile。

> 不要 `pnpm add <包> --no-catalog` 之类的绕过 —— 与仓库依赖治理约定冲突，CI 会再次失败。

## 6. 登录锁定（账号被锁 / 一直提示失败次数）

**症状**：连续输错密码后被锁 `X 分钟内无法登录`；或某个 IP 的请求全被拒。

**机制**（`auth/login-lock.service.ts`）：

- 账号失败计数 key：`auth:lock:{accountId}`；IP 计数 key：`auth:lock:ip:{ip}`；
- 默认：账号 5 次失败/15min 锁定，同 IP 50 次/15min 锁定，锁 15 分钟（`LOGIN_LOCK_TTL`）；
- **账号阈值优先级**：后台「系统设置」的 `settings.loginFailThreshold` > 环境变量 `LOGIN_LOCK_ACCOUNT_THRESHOLD` > 默认 5。

**解决**：

- 等锁定期结束，或清掉锁定 key：`redis-cli del "auth:lock:<accountId>" "auth:lock:ip:<ip>"`（或用管理后台「缓存管理」按模式删 `auth:lock:*`，如果还能登录）；
- 想调阈值：后台系统设置改 `loginFailThreshold`，或改环境变量后重启 server；
- 开发环境嫌烦：把 `LOGIN_LOCK_ACCOUNT_THRESHOLD` 调大 / `LOGIN_LOCK_TTL` 调小。

## 7. Redis 不可用 → 缓存降级

**症状**：Redis 挂了（容器没起、`REDIS_URL` 配错），但服务**没有崩**，只是日志出现缓存相关警告；登录锁定、验证码防重放等跨实例一致性的功能退化为单实例语义。

**机制**：`common/cache/cache.service.ts` 在 Redis 连接失败时自动降级为**内存后端**（`MemoryCacheBackend`），服务不中断。

**处理**：

```bash
docker compose up -d redis          # 或修复 REDIS_URL 后重启 server
```

> 降级是"可用性优先"设计：单实例开发环境无感；生产多副本时降级会导致锁定计数不共享，应尽快恢复 Redis。

## 8. lint 边界规则报错（lint:boundaries）

**症状**：`pnpm lint:boundaries`（ESLint）报 `A project tagged with "scope:xxx" can only depend on ...` 或 `enforce-module-boundaries` 错误；而 `pnpm lint`（oxlint）是绿的。

**原因**：分层设计 —— **oxlint 管代码规则，ESLint 只管 Nx 模块边界**（`@nx/enforce-module-boundaries` + `@nx/dependency-checks`），规则定义在 `eslint.config.mjs` 的 `depConstraints`。

**常见违规**：

- 前端直接 `import` 了 `@starter/contracts`（规定前端只从 `@starter/api-client` 取领域模型与校验 schema，不直接依赖 contracts）；
- 共享包反向依赖了 apps；
- 缺 `workspace:*` 依赖声明却 import 了兄弟包（`dependency-checks` 报）。

**解决**：按报错提示调整 import 来源或补 `package.json` 依赖，然后重跑：

```bash
pnpm lint:boundaries
```

## 9. Node / pnpm 版本不匹配

**症状**：pnpm 启动报 `SyntaxError: ... does not provide an export named 'styleText'`、`Unsupported engine`、`corepack: ... not found`。

**原因**：本机 Node 过旧（pnpm 11 要求 Node >= 22.13，仓库要求 >= 22.18；本指南测试环境就踩过 Node 20 的坑）。

**解决**：

```bash
nvm install 24 && nvm use 24        # 或 fnm / volta
node -v                              # >= 22.18
corepack enable
corepack prepare pnpm@11.21.0 --activate
pnpm -v                              # 11.21.0
```

## 10. CORS 跨域报错

**症状**：前端请求 3301 报 `blocked by CORS policy`（生产常见；开发一般有 Vite 代理不会触发）。

**原因**：后端默认只放行 `http://localhost:3302`；前端换了域名/端口、或生产直接跨域访问未配置。

**解决**：`apps/server/.env` 配置 `CORS_ORIGINS`（逗号分隔）后重启：

```bash
CORS_ORIGINS=https://admin.example.com,http://localhost:3312
```

> 生产走 nginx 同域反代（`/api`、`/graphql`、`/uploads`），一般不需要开跨域；只有 admin 与 server 不同域时才需要。

---

## 11. 环境变量校验失败（fail-fast）

**症状**：server 启动直接退出，报 `环境变量校验失败: JWT_SECRET: ...`。

**原因**：`src/config/env.validation.ts` 用 zod 全量校验，缺失/非法即拒绝启动（防"带病上线"）。

**解决**：按报错信息补齐 `apps/server/.env`（最常见是 `JWT_SECRET` 不足 16 字符、`DATABASE_URL` 为空）。
---

## 12. 通用排查三板斧

```bash
pnpm exec nx serve server            # 1) 看 server 日志（pino JSON 行，含 requestId）
curl http://localhost:3301/health/readiness   # 2) 验证服务自检
rm -rf node_modules/.cache .nx/cache apps/admin/dist apps/server/dist && pnpm install   # 3) 清生成物/缓存后重试
```
