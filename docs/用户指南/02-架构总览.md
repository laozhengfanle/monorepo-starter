## 1. 仓库结构（Nx + pnpm workspace）

```
monorepo-starter/
├── apps/                        # 可部署应用
│   ├── server/                  # NestJS 11 后端（GraphQL 为主 + 少量 REST），端口 3301
│   ├── admin/                   # React 19 管理后台（Vite 8 + antd 6），端口 3302
│   └── admin-e2e/               # Playwright 端到端测试
├── packages/shared/             # 共享库（只能被 apps 依赖，不能反向依赖 apps）
│   ├── contracts/               # zod 契约：后端入参/出参的单一事实源，前后端共享
│   ├── server-core/             # 后端基建：BizException / 异常过滤器 / Swagger / Zod 管道 / DTO
│   ├── api-client/              # orval 生成的 REST client（React Query hooks，axios）
│   ├── ui/                      # 前端共享 UI 组件与 antd 主题
│   └── test-utils/              # 测试工具
├── k8s/                         # Kubernetes manifests（kustomize）
├── docker-compose.yml           # 开发编排（postgres/redis/server/admin/adminer）
├── docker-compose.prod.yml      # 生产编排
├── nx.json                      # Nx 配置（插件、targetDefaults、generators）
├── pnpm-workspace.yaml          # workspace + catalog（catalogMode: strict）
└── docs/                        # 文档（本指南 + 架构流程图 + ERD + 命名规范）
```

依赖方向是**单向的**：

```
apps/admin ──► packages/shared/contracts（类型 + zod schema）
apps/admin ──► packages/shared/api-client（REST hooks）
apps/server ──► packages/shared/contracts、packages/shared/server-core
```

这条规则由 `pnpm lint:boundaries`（ESLint + Nx 依赖边界）强制检查，跨层 import 会在 CI 里报错。

## 2. 后端分层

`apps/server` 内部按"基础设施 → 业务模块"两层组织：

```
src/
├── main.ts                  # 入口：预载 .env → createApp() → listen(3301)
├── app-setup.ts             # createApp()：装配中间件/管道/过滤器/CORS/Swagger（可测试导入）
├── app/app.module.ts        # 根模块：注册全部全局设施 + 业务模块
├── config/                  # 环境变量 zod schema + fail-fast 校验（env.ts / env.validation.ts）
├── common/                  # 跨模块基建（见下）
├── health/                  # 健康检查（/health, /health/liveness, /health/readiness）
├── generated/               # 生成物（schema.gql 等，勿手改）
└── modules/                 # 业务模块：auth / admin-account / admin-role / admin-menu /
                             # audit-log / cache-admin / dashboard / file-manager /
                             # system-config / system-dict / turnstile / upload / ws
```

`common/` 基建一览（全部全局注册，业务模块无需感知）：

| 目录             | 职责                                                                              |
| ---------------- | --------------------------------------------------------------------------------- |
| `prisma/`        | PrismaService（driver adapter + UUIDv7 主键）                                     |
| `cache/`         | 缓存抽象（Redis 优先，不可用时自动降级内存后端）                                  |
| `graphql/`       | Code-First GraphQL 模块（Apollo + 自动生成 schema.gql + DataLoader + 错误归一化） |
| `dataloader/`    | DataLoader 工厂（每请求实例，解决菜单树/角色码 N+1）                              |
| `logger/`        | pino 结构化日志（requestId 串联）                                                 |
| `metrics/`       | Prometheus `/metrics` + 业务指标收集器（登录失败/限流/审计/上传/缓存命中）        |
| `notifications/` | 短信/邮件可插拔 Provider（默认 mock）                                             |
| `tasks/`         | @nestjs/schedule 定时任务（每日清理过期审计日志与 token 撤销记录）                |
| `storage/`       | 可插拔存储驱动（文件存储抽象）                                                    |
| `throttler/`     | 全局限流守卫（100 次/分钟/IP，GraphQL 兼容）                                      |

## 3. 前端分层

`apps/admin` 按 **features（业务切片）** 组织，公共能力在 `app/` 与 `shared/`：

```
src/
├── app/
│   ├── apollo-client.ts        # Apollo Client 实例（GraphQL 数据层）
│   ├── route-registry.tsx      # 路由注册表：path → 页面组件（+ 权限点）
│   ├── layouts/  providers/    # 布局与全局 Provider（QueryClient/Apollo/antd App）
│   └── auth/use-permission.ts  # 权限判断 hooks
├── features/                   # 业务切片（见《03-模块参考.md》）
│   ├── auth/                   # 登录页
│   ├── dashboard/              # 仪表盘
│   ├── admin-accounts|admin-roles|admin-menus/   # IAM 管理页
│   ├── account/                # 个人中心（资料/设置）
│   └── system/                 # 系统设置 5 页 + 字典页
├── shared/                     # 跨切片共享代码
└── generated/                  # 生成物：graphql.ts（codegen hooks）、api-client 产物
```

数据层双轨：

- **GraphQL（主力）**：Apollo Client + `@graphql-codegen` 从 `graphql/schema.gql` 生成类型化 hooks（`apps/admin/codegen.ts`）；
- **REST（辅助）**：orval 从 `openapi/openapi.json` 生成 React Query hooks（`packages/shared/api-client`），仅覆盖后端 REST 端点。

## 4. 前后端数据流

```
浏览器 (admin SPA)
   │
   ├─ GraphQL ──► /graphql ──► Apollo Server (Code-First) ──► Resolver ──► Service ──► Prisma ──► PostgreSQL
   │   (Apollo Client + codegen hooks)        (JwtAuthGuard + PermissionGuard + 限流 + DataLoader)
   │
   ├─ REST ────► /api/*（dev 代理剥离前缀）──► REST Controller（认证/上传/健康检查）──► Prisma
   │   (orval React Query hooks)
   │
   └─ 静态资源 ─► /uploads/*（dev 代理）────► server 的 express.static(uploads/)
```

- 开发时 admin 的 Vite 代理：`/api`（剥离前缀）、`/graphql`、`/uploads` → `localhost:3301`；
- 生产时由 admin 镜像里的 nginx 完成同样的反代（见《06-部署运维.md》）；
- 认证信息通过 `Authorization: Bearer <accessToken>` 传递，GraphQL 与 REST 共用同一套 JWT 守卫。

## 5. 关键设计决策

### 5.1 GraphQL 为主、REST 为辅

- **GraphQL** 是业务数据网关：所有面向页面/表格的读写都走 GraphQL（BFF 规范），前端按需取字段，后端在 Resolver 层聚合；
- **REST 仅保留必须场景**：认证登录（`auth.controller.ts`）、文件上传（`upload.controller.ts`）、健康检查（`health.controller.ts`）——这些场景天然是"单一动词 + 文件/流/探针"语义，用 REST 更合适；
- REST 的 OpenAPI 规范由后端发射到 `openapi/openapi.json`，orval 据此生成类型化 client，保证前后端契约一致。

### 5.2 契约先行（contracts 包）

- `packages/shared/contracts` 用 zod 定义请求/响应结构，是**后端入参校验**与**前端类型**的单一事实源；
- 后端用 `nestjs-zod` 全局管道校验，前端直接 `import` 类型，两边不会漂移。

### 5.3 权限模型

- 数据模型：`AdminRole ↔ AdminMenu ↔ 权限点`（`role:list`、`account:list`、`config:audit:view` 等）；
- 运行时：`PermissionGuard` 校验 `@RequirePermission('xxx:yyy')`，侧栏菜单来自 `me.menus`，前端 `usePermission` 控制显隐，路由表再兜底 403；
- 审计：AuditService 异步写入 `audit_log`（fail-open，不阻塞主流程）。

### 5.4 可靠性设计

- Redis 不可用时缓存自动降级内存后端（服务不中断，仅丢跨实例一致性）；
- 登录锁定支持后台设置（`system_config.settings.loginFailThreshold`）优先于环境变量；
- 健康检查三件套：基础信息 / liveness（进程存活）/ readiness（DB + 内存探活）。
