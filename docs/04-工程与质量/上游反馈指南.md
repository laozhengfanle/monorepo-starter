# 上游反馈指南（fork 项目向 monorepo-starter 提 Issue）

> 适用对象：**fork 或 clone 本项目开发真实业务**的开发者/AI 代理。
> 目标：开发过程中发现的 **starter 底座 bug / 不合理设计**，能规范、高效地回流到上游，
> 让上游与所有 fork 一起受益。规范摘要已写入 `AGENTS.md`（fork 时保留该块，AI 必读）。

---

## 1. 判断：这是不是"上游问题"？

先判断问题归属，再决定提不提：

| 场景                                                                                                                        | 归属                             | 动作                     |
| --------------------------------------------------------------------------------------------------------------------------- | -------------------------------- | ------------------------ |
| 问题出在 starter 通用能力：认证/权限/RBAC、审计、限流、缓存、上传、系统配置、GraphQL/REST 基础设施、seed、文档、CI/部署模板 | **上游**                         | 提 Issue                 |
| 未改动相关代码，按文档/示例操作仍不符合预期                                                                                 | **上游**（多半是文档或实现 bug） | 提 Issue                 |
| 文档与代码行为不一致                                                                                                        | **上游**                         | 提 Issue（这是文档 bug） |
| 问题出在 fork 后新增的业务逻辑 / 字段 / 模块 / 页面                                                                         | **业务**                         | 自己修，不提上游         |

> 判别技巧：`git log -- <相关文件>` 看该文件在你 fork 后是否被改过；没改过却出问题 → 上游。

---

## 2. 提交到哪里

上游仓库：**https://github.com/laozhengfanle/monorepo-starter**

路径：`Issues → New Issue → Bug 报告`（模板：`.github/ISSUE_TEMPLATE/bug_report.md`）

---

## 3. 提交方式（按环境选其一）

### 方式 A：gh CLI（有上游写权限时）

```bash
gh issue create --repo laozhengfanle/monorepo-starter \
  --title "[bug] <一句话概述>" \
  --body "$(cat <<'EOF'
## 描述
<现象>

## 复现步骤
1. ...

## 环境
- 上游版本：2.0.0
- 操作系统：macOS 12.7.6
- Node：24 / pnpm：11.21.0
- 涉及：apps/server/src/modules/auth/...

## 来源说明
fork 后开发；相关代码**未改动**
EOF
)"
```

### 方式 B：预填链接（无写权限时，**最常见**）

生成一条带标题+正文的链接，交给用户在浏览器打开即进入预填好的新建 Issue 页：

```
https://github.com/laozhengfanle/monorepo-starter/issues/new?title=[bug]+<概述>&body=<模板字段，URL 编码>
```

AI 生成链接时应把 **标题与正文字段（描述/复现/期望/实际/环境/来源）**全部 URL 编码进 `body`。

### 方式 C：草稿粘贴

AI 写好完整 Markdown（按模板字段），输出给用户，用户手动 New Issue 粘贴提交。

---

## 4. 必填信息（对照模板）

| 字段                          | 说明                                                             |
| ----------------------------- | ---------------------------------------------------------------- |
| 上游版本                      | `apps/admin/src/app/version.ts` 的 `APP_VERSION`（如 `2.0.0`）   |
| 描述 / 复现步骤 / 期望 / 实际 | 缺一不可；附截图/日志更佳                                        |
| 环境                          | OS / Node / pnpm / 涉及的应用与包                                |
| 来源说明                      | 是否 fork；**fork 是否改动过相关代码**（关键：决定上游是否受理） |

---

## 5. 红线

- **禁止**在 issue 中放入业务敏感数据：密钥、token、内部域名/地址、真实用户数据；
- 未经用户确认，不得发布任何内容（AI 生成草稿/链接后，**提交动作由用户执行或用户确认后执行**）；
- 不要为"业务代码问题"刷上游 issue。

---

## 6. 后续闭环

- 提交 issue 后**不改上游**：本地可用 workaround 继续开发；
- 上游修复后可 `git pull` / cherry-pick 合并；
- 若你愿意，也可直接提 **PR** 修复（fork → 修改 → PR 到上游），上游维护者会 review。
