# 测试策略

> 本文介绍项目的测试分层与约定：Vitest 单元/集成测试、80% 覆盖率阈值、Playwright e2e，以及测试文件组织方式。

## 1. 测试金字塔与工具

| 层        | 工具                      | 位置                                  | 说明                                                       |
| --------- | ------------------------- | ------------------------------------- | ---------------------------------------------------------- |
| 单元/集成 | Vitest 4                  | 与源码同目录 `*.spec.ts`              | 服务/守卫/工具，`Test.createTestingModule` + `vi.fn` 桩    |
| e2e       | Playwright                | `apps/admin-e2e/`                     | 浏览器端到端（登录 → 主流程冒烟）                          |
| API e2e   | Vitest（superagent 风格） | `apps/server/src/app/api.e2e.spec.ts` | 完整应用装配后的接口级验证（导入 `createApp`，不监听端口） |

根 `vitest.config.mts` 聚合各项目配置（`projects` 匹配 `**/vitest.config.*`）；server 的配置见 `apps/server/vitest.config.mts`。

## 2. 单元测试：Test.createTestingModule + vi.fn

典型模式（参考 `dashboard.service.spec.ts`）：

```ts
import { Test } from '@nestjs/testing';
import { vi, describe, expect, it, beforeEach } from 'vitest';
import { DashboardService } from './dashboard.service.js';
import { PrismaService } from '../../common/prisma/prisma.service.js';

function createPrismaStub(overrides = {}): PrismaService {
  return {
    client: {
      account: { count: vi.fn().mockResolvedValue(3) },
      auditLog: { count: vi.fn().mockResolvedValue(100) },
      ...overrides,
    },
  } as unknown as PrismaService;
}

describe('DashboardService', () => {
  let service: DashboardService;

  beforeEach(async () => {
    const moduleRef = await Test.createTestingModule({
      providers: [DashboardService, { provide: PrismaService, useValue: createPrismaStub() }],
    }).compile();
    service = moduleRef.get(DashboardService);
  });

  it('getStats 返回统计卡片', async () => {
    const stats = await service.getStats();
    expect(stats).toHaveLength(4);
  });
});
```

约定：

- **依赖一律桩掉**：`PrismaService` 用 `useValue` 桩（`client` 上每个方法 `vi.fn().mockResolvedValue(...)`），不连真实数据库；
- 跨模块依赖用 token 替换（如 `CACHE_SERVICE_TOKEN` 注入内存实现或桩）；
- 断言行为而非实现：mock 返回值 → 调服务 → 断言结果与调用参数；
- 涉及定时任务/守卫的用例，参考 `cleanup.task.spec.ts`、`login-lock.service.spec.ts` 的模式（断言 deleteMany 的 where、锁定判定等）。

## 3. 覆盖率阈值

`apps/server/vitest.config.mts` 配置 v8 覆盖率：

```ts
coverage: {
  provider: 'v8',
  include: ['src/**/*.{ts,tsx}'],
  exclude: ['src/generated/**', 'src/main.ts', 'src/test-setup.ts', '**/*.spec.ts', '**/*.test.ts'],
  thresholds: { lines: 80, statements: 80, functions: 80, branches: 60 },
},
```

- **lines / statements / functions 阈值 80%**；**branches 阈值 60%**（2026-08 审计修复后实测 63%，较基线 49.5% 提升；剩余分支缺口集中在 cache 降级/通知 provider/throttler 守卫等，达 80% 为迭代项，见《审计修复计划.md》P1-6）；
- `exclude` 排除 **gitignored 的生成客户端**（`src/generated/**`，0% 覆盖会严重拖低阈值）与入口/测试基建；
- 低于阈值 CI 会失败（`pnpm test` / CI 的 affected test）；
- 报告输出到 `apps/server/test-output/vitest/coverage`；
- 新模块提交前本地跑 `pnpm exec nx test server` 确认达标。

## 4. Playwright e2e

- 位置：`apps/admin-e2e/`，配置 `playwright.config.ts`，用例 `src/smoke.spec.ts`、`src/login.spec.ts`、`src/key-flows.spec.ts`（登录/权限裁剪/登出关键流程）；
- 运行：`pnpm e2e`（nx run-many -t e2e），CI 中先 `pnpm exec playwright install --with-deps chromium`；
- 本地跑指定应用：`pnpm exec nx e2e admin-e2e`；
- 建议用例范围：登录 → 主菜单可达 → 一个核心业务闭环（如账户列表），保持冒烟级稳定，避免脆弱的 UI 细节断言（antd 两字按钮会插入空格，选择器注意）。

> **环境要求**：Playwright 1.62 需要 **macOS 13+ 或 Linux** 才能下载浏览器。macOS 12（Monterey）已不再受支持，`pnpm exec playwright install chromium` 会报 `Playwright does not support chromium on mac12`——请在 Linux 容器或 CI（GitHub Actions 的 Ubuntu 环境）中运行 e2e。

## 5. 组织约定

- **与源码同目录**：`*.spec.ts` 紧跟被测文件（`dashboard.service.spec.ts` 在 `dashboard.service.ts` 旁），便于就近维护与发现；
- 命名：`xxx.service.spec.ts` / `xxx.guard.spec.ts` / `xxx.constants.spec.ts`；
- 集成测试（需应用装配）放 `apps/server/src/app/api.e2e.spec.ts`（导入 `createApp()`，不监听端口，无副作用）；
- e2e 独立在 `apps/admin-e2e/`，不混入应用源码。

## 6. 运行命令

```bash
pnpm test                          # 全仓测试（nx run-many -t test）
pnpm exec nx test server           # 只跑 server
pnpm exec nx test admin-e2e        # e2e（Playwright）
pnpm e2e                           # 全部 e2e
pnpm exec nx test server --coverage # 本地查覆盖率报告
```

## 7. 测试纪律

- 新功能必须带测试：服务逻辑 → 单测；权限/限流 → 守卫/拦截器测试；页面闭环 → e2e；
- 不要为覆盖率凑用例：优先覆盖分支（错误分支、fail-open 分支、super_admin 绕过）；
- mock 数据用工厂函数（`createPrismaStub(overrides)`），避免大段重复；
- 测试失败先看是断言问题还是实现问题，CI 全绿是合入硬门槛（见《CI-CD.md》）。
