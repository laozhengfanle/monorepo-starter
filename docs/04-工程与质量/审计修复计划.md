## P0 —— 安全关键与部署可用性（建议立即，阻塞发布）

### P0-1. 修复 refresh token 撤销链路（报告 S1）｜M

**涉及文件**

- `apps/server/src/modules/auth/token-issuance.service.ts`（`refresh`）
- `apps/server/src/modules/auth/token-blacklist.service.ts`（`revokeAccountTokens` / `revokeToken` / `isRevoked`）
- 新增测试：`apps/server/src/modules/auth/token-issuance.service.spec.ts`、`auth.service.spec.ts`、`api.e2e.spec.ts`

**修复方案**

1. `refresh()` 补齐与 `JwtAuthGuard` 一致的校验：查账户（select enabled/tokenVersion）→ 不存在/禁用/`payload.tokenVersion !== account.tokenVersion` 一律 401。
2. `revokeAccountTokens` 按注释补写 `accountId` 维 `'*'` 撤销行（`tokenRevocation.create({ jti: '*', expiresAt: now+7d })`）或设 `auth:revoked:account:{id}` 缓存键；同时保留 tokenVersion++ 与缓存清理。
3. `revokeToken(jti)` 接通调用方（目前零调用）或删除并同步删 `isRevoked` 死分支。
4. 审计 detail 中记录撤销原因（沿用现有 `RevocationReason`）。

**验收标准**

- 新增集成测试：登录 → logout 后旧 refresh 调 `/auth/refresh` 必须 401；登录 → changePassword 后旧 refresh 必须 401；正常 refresh 流程仍通过。
- 并发 refresh 重用检测（setnx）行为不变，现有 `token-issuance.spec` 全绿。

### P0-2. 修复 K8s 部署资产（报告 S2）｜M

**验收标准**

### P1-7. 前端 token 存储改造（报告 H8）｜L

**涉及文件**：`apps/server/src/modules/auth/auth.controller.ts`（Set-Cookie）、`apps/admin/src/app/auth/auth-storage.ts`、`auth-context.tsx`、`auth-api.ts`、`packages/shared/api-client/src/axios-instance.ts`

**修复方案**

1. 后端：登录/refresh 响应通过 `Set-Cookie: HttpOnly; SameSite=Strict; Secure` 下发 access token（CSRF 面评估：SameSite=Strict + 自定义头校验），REST 保留 body 字段兼容期。
2. 前端：改为 cookie 自动携带（`withCredentials`），内存态持有用户信息；401 拦截逻辑同步调整。

**验收标准**

- 登录后 cookie 可见且 JS 不可读（document.cookie 不含 token）；登出/401 清理 cookie；e2e 登录流程通过。
