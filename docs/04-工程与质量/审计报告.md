## 2. 严重（2 项）—— 必须优先修复

### S1. Refresh Token 撤销链路断裂：登出/改密后 7 天内旧 refresh token 仍可换新会话

**涉及文件**

- `apps/server/src/modules/auth/token-blacklist.service.ts:38-47`（`revokeAccountTokens`）
- `apps/server/src/modules/auth/token-blacklist.service.ts:50-61`（`revokeToken`，死代码）
- `apps/server/src/modules/auth/token-issuance.service.ts:79-125`（`refresh`）

**证据**

1. `revokeAccountTokens` 注释（:20-21）声称「tokenVersion 自增 + jti='\*' 通配记录 + 清缓存」，但实现**从未写入 `token_revocation` 表的 `'*'` 行**，只做 `tokenVersion++` + 清 `auth:refresh:{accountId}:*` 缓存。
2. 唯一写 `token_revocation` 表的 `revokeToken()` **全仓无调用方**（死代码），`isRevoked` 的 DB 分支（含 `'*'` 匹配）永不命中。
3. `refresh()` 只做验签 + `isRevoked` + setnx 认领，**不校验 `payload.tokenVersion` 与 DB 当前值、不校验账户 enabled/存在**。对比 `jwt-auth.guard.ts:63`（access token 会因 tokenVersion 失效），refresh 是唯一缺口。
4. 放大效应：`revokeAccountTokens` 清空 `auth:refresh:{accountId}:*` 缓存，反而把 reuse 检测的 `active` 标记删掉，使 setnx 认领**必然成功**。

**攻击链**：窃取 refresh token → 受害者登出/改密（tokenVersion 自增）→ 攻击者 `POST /auth/refresh` 仍成功，且 `issueTokens` 会取 DB **当前** tokenVersion 签发新 access token → 通过 `JwtAuthGuard` 完全接管会话。

**修复方案**（见修复计划 P0-1）

1. `refresh()` 补齐与 `JwtAuthGuard` 一致的校验：账户存在 + enabled + `payload.tokenVersion === account.tokenVersion`；
2. `revokeAccountTokens` 按注释补写 `accountId` 维 `'*'` 撤销行（或设 `auth:revoked:account:{id}` 缓存键）；
3. 补集成测试：logout / changePassword 后 `refresh` 必须 401（现有 40+ 测试**零覆盖**此场景）。

### S2. K8s 一键部署资产整体不可用（`kubectl apply -k k8s/` 起不来）

**涉及文件**：`k8s/server-deployment.yaml`、`k8s/admin-deployment.yaml`、`k8s/ingress.yaml`、`k8s/kustomization.yaml`、`apps/admin/nginx.conf`

**证据（均为 apply 成功但 pod 起不来的静默失败）**

1. `k8s/server-deployment.yaml:49-52`：`volumeMounts` 引用卷名 `uploads`，但 pod spec **无 `volumes:` 段**，仓库也无 `server-uploads` PVC manifest（`k8s/postgres-pvc.yaml` 未纳入 kustomization）→ 无法调度。
2. `k8s/server-deployment.yaml:44-48`：`envFrom` 引用 `server-config` ConfigMap + `server-secrets` Secret，k8s/ 下**无这两个资源**、文档未给键清单 → CreateContainerConfigError。
3. `k8s/kustomization.yaml:28-33`：镜像为 `<registry>/...` 占位符 + `newTag: latest` → 拉取不存在镜像。
4. `apps/admin/nginx.conf:60,73,86`：反代上游硬编码 `server:3301`（compose 服务名），k8s Service 名为 `server-service` → 502。
5. `k8s/ingress.yaml:26-32`：`/api` 前缀直接转发 server，但 server **无全局 `/api` 路由**（vite/nginx 均在剥离 `/api`）→ 404。
6. `k8s/admin-deployment.yaml:26-31`：`readOnlyRootFilesystem: true` 但未给 nginx 的 `/var/cache/nginx`、`/var/run` 提供可写卷（compose prod 用 tmpfs 解决了，k8s 漏了）→ CrashLoopBackOff。

**修复方案**（见修复计划 P0-2）：补 PVC/ConfigMap/Secret 模板与键清单、nginx 上游改用变量注入、ingress 加 rewrite 或移除 `/api`、admin 挂 emptyDir、kustomization 纳入 postgres-pvc 并改 overlay 注入镜像，最后 `kubectl apply --dry-run=server -k k8s/` 验证。

## 3. 高（8 项）

### H1. CI 安全审计门当前必红

- `pnpm audit --audit-level=high` 退出码 1：`deepmerge-ts@7.1.5`（GHSA-ggr8-5vv4-36mx，递归对象合并栈耗尽 DoS）经 `@prisma/config → prisma → @prisma/client` 链路引入。
- `pnpm-workspace.yaml` 的 `overrides` 未覆盖、`audit.ignore` 未列入（现有 ignore 仅 GHSA-w3rx-r6r6-pgpr / GHSA-5p2g-fcmc-qvqq 两条）。
- 附带问题：本机 registry 为 npmmirror（无 audit 端点），本地 `pnpm audit` 开箱即不可用，需 `--registry=https://registry.npmjs.org`。
- 修复：升级 deepmerge-ts 到 ≥8（或加 override），或列入 audit.ignore 并附理由；本地 registry 问题建议在 `.npmrc` 项目级配置中解决或文档化。

### H2. 覆盖率门槛不达标 → CI test job 必红

- `apps/server/vitest.config.mts:17-22` 阈值 80%，实测 **lines 71.33 / statements 73.42 / functions 76.61 / branches 49.51**。
- `ci.yml` 的 `nx affected -t test --coverage` 会失败。分支覆盖率近半是明显短板（守卫/异常分支大量未测）。
- 修复：补测试（优先 permission.guard / jwt-auth.guard / exception.filter / 各 service 异常分支），或先核实 CI 实际行为并降阈值（不推荐）。

### H3. 角色权限编辑可提权（非超管自我提权）

- `apps/server/src/modules/admin-role/admin-role.service.ts:64-94`（create）、`:96-154`（update）、`:183-198`（bindPermissions）：**无操作者持有权限校验**。持 `role:update`/`role:create` 的非超管可给任意角色（含自己已绑定的角色）添加任意权限点（`config:admin:update`、`account:update` 等全部）→ 等效自我提权；也可篡改其他角色。
- 对比 `admin-account.service.ts:616-635` 的 `assertAssignableRoles` 有同类护栏，role 模块缺失。
- 修复：非超管仅允许修改自己持有的角色，且授予的权限点 ⊆ 自己已持有（复用 `resolveAccountPermissions` 判定，与 `assertMenusWithinOwnedPermissions` 对齐）；`menu:create` 的 code 亦需限制（配合 H3 残余风险）。
- **勘误**：子代理原报「菜单 code 可改名提权」经复核**不成立**——`UpdateMenuSchema`（`packages/shared/contracts/src/lib/schemas/admin-menu.ts:57-66`）不含 `code` 字段，`admin-menu.service.ts update()` 无法改 code；但「create 任意 code + bindPermissions 无持有校验」的组合提权链仍成立，已并入本条。

### H4. 非超管可降权/禁用其他管理员（含超管）

- `apps/server/src/modules/admin-account/admin-account.service.ts:236-257`（`assertAssignableRoles`）+ `:689-709`（`assertSuperAdminRemains`）：`roleCodes` 为**全量替换语义**，校验只拦「授予 super_admin」、不拦「移除 super_admin」；兜底只保证「还剩至少一个启用超管」→ 持 `account:update` 者可把除最后一位外的所有超管逐一降权/禁用（可用性攻击 + 越权降权）。
- 修复：移除 super_admin 角色、禁用 super_admin 账户强制要求操作者本人为超管。

### H5. cache-admin 越权（读未脱敏密钥 / 清安全类缓存键）

- `apps/server/src/modules/cache-admin/cache-admin.service.ts:31-59`（listKeys）、`:62-80`（getValue）：返回缓存**原始值**——`sys:config:turnstile.config` / `sys:config:storage.driver` 缓存存含 `secretKey`/`accessKey` 的完整 JSON（脱敏只在 `system-config.service.ts:137-149` 的 DB 读取路径，缓存读不脱敏）→ 持 `config:cache:view` 即可读密钥。
- `:83-92`（delete）/ `:95-113`（deleteKeys）/ `:116-129`（clearByPattern）：无 key 命名空间限制——`clearByPattern('auth:lock:*')` 绕过登录锁定，`clearByPattern('turnstile:used:*')` 重放人机验证。
- 修复：读写加安全前缀白名单（禁 `auth:*` / `sys:config:*`，或对 `sys:config:*` 值做同款脱敏）；安全键删除需超管或二次确认。

### H6. 上传端点无限流 → 磁盘填充 DoS

- `apps/server/src/modules/upload/upload.controller.ts:47-88`：无 `@Throttle`（全局限流 100/min 每 IP），任意登录用户 100 次/min × 10MB ≈ **1GB/min 落盘**。
- 修复：`@Throttle`（如 10/min）+ 账号级每日配额 + 磁盘水位告警。

### H7. 生产数据库迁移无可行路径

- `docs/05-用户指南/06-部署运维.md:92-94` 推荐 `docker compose exec server pnpm exec prisma migrate deploy`，但 `prisma` 是 devDependency，`apps/server/Dockerfile:65` runtime 阶段 `pnpm install --prod` **不含 prisma CLI**；「方式二（CI 执行）」也从未实现（deploy.yml 无迁移步骤）→ 生产首次建表/升级无门。
- 修复：镜像内嵌迁移能力（prisma 列入 prod 依赖或独立 migration 镜像/Job），并在 deploy.yml 增加 pre-deploy migrate 步骤；修正文档。

### H8. 前端 access token 存 localStorage

- `apps/admin/src/app/auth/auth-storage.ts:13,16`：token 明文存 `localStorage`（key `admin_access_token`），同源任意脚本可读；一旦出现 XSS（含未来引入的富文本/第三方脚本）即账户接管。
- 现状缓解：当前代码无 `dangerouslySetInnerHTML`、富文本已前后端 DOMPurify 双清洗（`rich-editor.tsx:129,132` + `sanitize-html.ts`）、无敏感 console.log、权限四层控制——无已知活跃注入点，但属 OWASP 明确建议整改项。
- 修复：改 httpOnly + SameSite=Strict cookie（后端 Set-Cookie，配合已存在的 refresh 端点），前端仅内存态；或至少降级 sessionStorage + 缩短有效期。
