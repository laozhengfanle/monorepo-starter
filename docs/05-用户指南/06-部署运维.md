# 06 部署运维

> Docker 构建 / Compose 编排（开发 + 生产）/ K8s 部署 / 健康检查 / 日志 / 监控指标。
> 所有部署资产都在仓库根目录：`docker-compose.yml`、`docker-compose.prod.yml`、`k8s/`、`apps/*/Dockerfile`。

---

## 1. 镜像构建

后端（NestJS webpack 产物，多阶段构建）：

```bash
docker build -f apps/server/Dockerfile -t monorepo-starter-server .
```

管理端（Vite 构建 + nginx 静态服务与反代）：

```bash
docker build -f apps/admin/Dockerfile -t monorepo-starter-admin .
```

> 构建时间较长是正常的（Stage 1 全量安装依赖含 prisma/swc 等构建工具）；镜像内 Node 24 + pnpm 11 由 corepack 锁定（与 `.nvmrc`=24 / CI node 24 对齐，P2-10 版本统一）。
> server 镜像运行时非 root 用户（UID 1001）+ dumb-init，PID 1 能正确响应 SIGTERM（k8s 优雅关闭依赖它）；Dockerfile 带 `HEALTHCHECK`（探测 `/health/liveness`，进程级基线，readiness 由编排层负责）。

## 2. 开发编排（docker compose up）

`docker-compose.yml` 起 **postgres / redis / server / admin / adminer** 五个服务：

```bash
docker compose up -d            # 默认端口即可（见下）
docker compose ps               # 查看状态
docker compose logs -f server   # 跟随后端日志
```

| 服务     | 端口（宿主机） | 说明                                      |
| -------- | -------------- | ----------------------------------------- |
| postgres | 127.0.0.1:5432 | PG 17，健康检查 `pg_isready`              |
| redis    | 127.0.0.1:6379 | Redis 7                                   |
| server   | 127.0.0.1:3301 | 开发编排内 `develop.watch` 同步源码热重载 |
| admin    | 127.0.0.1:3302 | nginx 静态服务 + 反代                     |
| adminer  | 127.0.0.1:8080 | 数据库管理（**dev-only**）                |

自定义端口/凭据通过根目录 `.env`（模板 `.env.example`）覆盖：

```bash
cp .env.example .env
# 改 SERVER_PORT / ADMIN_PORT / POSTGRES_PASSWORD 等
docker compose up -d
```

> 端口只绑定 `127.0.0.1`（不暴露公网）；server 依赖 postgres/redis 健康后才启动。

## 3. 生产编排（docker compose -f docker-compose.prod.yml）

生产编排**不含 adminer**，全部服务限制资源（cpus/memory/pids_limit）、`no-new-privileges`、非 root 运行、只读根文件系统 + tmpfs。

```bash
# 1) 准备生产环境变量（必填项缺失会启动失败）
cat > .env.production <<'EOF'
POSTGRES_PASSWORD=<强密码>
JWT_SECRET=<至少16字符随机串>
CORS_ORIGINS=https://admin.example.com
IMAGE_REGISTRY=ghcr.io
IMAGE_REPOSITORY_OWNER=your-org
IMAGE_TAG=<真实版本 tag，如 v1.2.3；禁止 latest>
LOG_LEVEL=info
EOF

# 2) 启动
docker compose -f docker-compose.prod.yml --env-file .env.production up -d

# 3) 查看状态与日志
docker compose -f docker-compose.prod.yml --env-file .env.production ps
docker compose -f docker-compose.prod.yml --env-file .env.production logs -f server
```

要点：

- `JWT_SECRET` / `POSTGRES_PASSWORD` / `IMAGE_REPOSITORY_OWNER` / `IMAGE_TAG` 用 `${VAR:?}` 声明 —— **不设置直接启动失败**（fail-fast，防止弱默认值/占位仓库/`latest` 上线）；
- 生产编排使用**已推送的镜像**（`IMAGE_REGISTRY/IMAGE_REPOSITORY_OWNER/IMAGE_TAG`），不走本地 build；`IMAGE_TAG` 禁止 `latest`（发布不可复现）；
- 生产编排里 server（UID 1001）、admin（nginx uid 101）、postgres（uid 70）、redis（uid 999）全部显式非 root 运行；
- server 的健康检查打 `/health/readiness`（依赖 DB，比 dev 的 `/health` 更严格）。

数据库迁移（首次或版本升级时）：

> server 运行时镜像用 `pnpm install --prod`（prisma 是 devDependency，已裁掉），**没有 prisma CLI**。
> 因此生产迁移改走专用 **migration 镜像**（server 镜像的 `--target migration` 阶段，含 prisma CLI + schema + migrations），
> 迁移镜像只在发布期构建/使用，不占运行时镜像体积。

```bash
# ① 构建迁移镜像（含 prisma CLI + schema + migrations）——通常由 CD（deploy.yml）在发布时自动构建/拉取
docker build --target migration -t monorepo-starter-migration:<tag> -f apps/server/Dockerfile .

# ② 对数据库执行迁移（迁移先行，成功后才会起新副本）
#    - --network <project>_default：加入 compose 生产网络，使 `postgres` 服务名可解析
#    - -e DATABASE_URL：迁移所需的连接串（从 .env.production 取 POSTGRES_* 拼出）
NET_NAME="$(docker compose -f docker-compose.prod.yml --env-file .env.production config --format json | jq -r .name)_default"
DB_URL="postgresql://${POSTGRES_USER:-postgres}:${POSTGRES_PASSWORD:?}@postgres:5432/${POSTGRES_DB:-monorepo_starter}?schema=public"
docker run --rm --network "$NET_NAME" -e DATABASE_URL="$DB_URL" \
  monorepo-starter-migration:<tag> migrate deploy

# ③（可选）注入主数据 seed（幂等，空库/缺数据时用；生产有数据可跳过）
docker run --rm --network "$(docker compose -f docker-compose.prod.yml --env-file .env.production config --format json | jq -r .name)_default" \
  -e DATABASE_URL="..." \
  monorepo-starter-migration:<tag> db seed
```

> **发布流程里迁移是前置步骤**：deploy.yml 在 `docker compose up` **之前**执行 `migrate deploy`，任一迁移失败即中止（`set -e`），避免新代码打旧库。`migrate deploy` 只应用已存在的迁移、不修改 schema。

## 4. Kubernetes 部署

`k8s/` 目录提供 kustomize manifests：

```
k8s/
├── namespace.yaml              # monorepo-starter 命名空间
├── postgres-statefulset.yaml   # PostgreSQL（headless service + 持久卷模板）
├── postgres-pvc.yaml           # PG 持久卷声明（独立资源）
├── redis-statefulset.yaml      # Redis
├── server-uploads-pvc.yaml     # server 上传文件持久卷
├── server-config.yaml          # server 明文环境变量（ConfigMap 模板）
├── server-secrets.yaml         # server 敏感变量（Secret 模板，**不要直接 apply**）
├── server-deployment.yaml      # 后端 Deployment（探针 / 资源 / 优雅关闭 / 上传卷 / /tmp emptyDir）
├── admin-deployment.yaml       # 管理端 Deployment（emptyDir /var/cache/nginx /var/run + UPSTREAM_SERVER 注入）
├── ingress.yaml                # 入口（server + admin 路由；/api 用 rewrite-target 剥前缀）
└── kustomization.yaml          # 汇总入口（含部署顺序注释）
```

### 4.1 完整部署流程

```bash
# 0. 准备 kubectl 上下文（指向目标集群）
kubectl config use-context <cluster-name>

# 1. 编辑 server-config.yaml，把占位 <替换> 改成实际值（必填 DATABASE_URL、REDIS_URL、CORS_ORIGINS）
$EDITOR k8s/server-config.yaml

# 2. 创建 postgres 凭据（Secret 不入库）
kubectl -n monorepo-starter create secret generic postgres-credentials \
  --from-literal=username=postgres --from-literal=password='<强密码>'

# 3. 创建 server-secrets（**不要**直接 apply k8s/server-secrets.yaml，里面是占位）
JWT_SECRET=$(openssl rand -hex 32)
kubectl -n monorepo-starter create secret generic server-secrets \
  --from-literal=JWT_SECRET="$JWT_SECRET"
unset JWT_SECRET

# 4. 替换镜像 tag（默认 newTag 仅为占位 0.0.0；生产用 kustomize edit set image 改成真实版本）
cd k8s
kustomize edit set image \
  server=ghcr.io/your-org/monorepo-starter-server:v1.2.3 \
  admin=ghcr.io/your-org/monorepo-starter-admin:v1.2.3
cd -
# 注意：newTag 禁止 latest（生产不可复现）

# 5. 一键部署（kustomization resources 顺序：namespace → statefulset → pvc → config → deployment → ingress）
kubectl apply -k k8s/

# 6. 观察就绪
kubectl -n monorepo-starter get pods -w
# 期望：postgres/redis 1/1，server/admin 2/2，ingress 有 ADDRESS

# 7. 验证关键路径
curl -fsS https://api.example.com/auth/login -X POST -H 'content-type: application/json' \
  -d '{"username":"root","password":"Root!123"}'   # 期望 201 + 双 token
curl -fsSI https://admin.example.com/             # 期望 200，nginx SPA fallback
```

### 4.2 关键设计说明

- **反代上游**：`admin-deployment` 通过 env `UPSTREAM_SERVER=server-service:3301` 注入，admin 容器的 entrypoint 跑 `envsubst` 把 `nginx.conf` 模板里的 `${UPSTREAM_SERVER}` 替换为实际值并写到 `/var/cache/nginx/default.conf`（emptyDir 挂载，readOnlyRootFilesystem 友好）。compose 下用 `UPSTREAM_SERVER=server:3301`，同一份镜像同时支持两套部署。
- **/api 路径重写**：`server-ingress` 的 `/api` path 用 `ImplementationSpecific` + `rewrite-target: /$2`，把 `/api/auth/login` 剥成 `/auth/login` 转发给 server（NestJS 控制器无 `/api` 前缀）。
- **限流注解**：`nginx.ingress.kubernetes.io/limit-rps: '100'`（合法注解；旧的 `rate-limit` 是非法注解已删除）。
- **postgres 用户对齐**：`postgres:17-alpine` 镜像内置 `postgres` uid=70，statefulset `runAsUser/runAsGroup/fsGroup=70`（不是 999）。
- **server 上传卷**：单副本 `ReadWriteOnce`；多副本需 ReadWriteMany 存储类（`server-uploads-pvc.yaml` 注释里说明）。
- **数据库迁移**：发布时**迁移先行**——deploy.yml 在 `docker compose up` **之前**用 migration 镜像跑 `prisma migrate deploy`（失败即中止发布）；手动执行见第 3 节（migration 镜像方式），**不要**在 server 容器里跑（runtime 镜像无 prisma CLI）。

### 4.3 卸载

```bash
kubectl delete -k k8s/                                  # 删全部资源
kubectl delete -n monorepo-starter secret postgres-credentials server-secrets  # 删 Secrets（kustomization 不管）
kubectl delete pvc -n monorepo-starter --all            # 删 PVC（数据卷，慎用）
```

## 5. 健康检查端点

| 端点                    | 用途                                                          | 依赖                   |
| ----------------------- | ------------------------------------------------------------- | ---------------------- |
| `GET /health`           | 基础信息（service / version），前端展示用                     | 无                     |
| `GET /health/liveness`  | 存活探针（livenessProbe）：进程活着即 200                     | 无（**不查外部依赖**） |
| `GET /health/readiness` | 就绪探针（readinessProbe）：DB `SELECT 1` + 内存 heap < 300MB | PostgreSQL             |
| `GET /healthz`          | admin 容器 nginx 健康检查（wget 探测）                        | 无                     |

验证：

```bash
curl -s http://localhost:3301/health
curl -s http://localhost:3301/health/liveness
curl -s http://localhost:3301/health/readiness   # 依赖 DB 就绪
```

## 6. 日志

- 后端使用 **pino 结构化日志**（JSON 行），requestId 串联请求链路；级别由 `LOG_LEVEL` 控制；
- 本地开发：直接看终端；容器：`docker compose logs -f server` / `kubectl -n monorepo-starter logs -f deploy/server`；
- 生产建议接入集中日志（如 Loki/ELK），把容器 stdout 采集走即可，无需改代码；
- 排障常用：`docker compose logs --tail=200 server`、`kubectl describe pod <pod>`（看探针/镜像拉取失败原因）。

---

## 7. 监控指标（Prometheus）

- 端点：`GET /metrics`（`@willsoto/nestjs-prometheus`，含 Node.js 运行时默认指标）；
- 业务指标（`common/metrics/business.metrics.ts`）：登录失败计数、限流拦截计数、审计写入计数、上传计数、缓存命中率等 —— 业务代码注入 `BusinessMetrics` 后调用语义方法埋点；
- 接入方式：Prometheus 抓取 `http://<server>:3301/metrics`，Grafana 出面板；CI 里可用 Trivy/审计任务保证镜像安全（见 08-Changelog 的 CI 全链路）。

## 8. 常用运维速查

| 操作           | 命令                                                                          |
| -------------- | ----------------------------------------------------------------------------- |
| 本地起全套 dev | `docker compose up -d`                                                        |
| 起生产编排     | `docker compose -f docker-compose.prod.yml --env-file .env.production up -d`  |
| 看日志         | `docker compose logs -f server`（生产编排加 `-f ... --env-file` 参数）        |
| 重建某服务     | `docker compose up -d --build server`                                         |
| 停止/清理      | `docker compose down`（`-v` 会删数据卷，慎用）                                |
| 生产迁移       | migration 镜像跑 `migrate deploy`（见第 3 节；deploy.yml 已作为发布前置步骤） |
| K8s 部署       | `kubectl apply -k k8s/`（详见 4.1 完整流程）                                  |
| 健康检查       | `curl http://localhost:3301/health/readiness`                                 |
| 监控           | `curl http://localhost:3301/metrics`                                          |
