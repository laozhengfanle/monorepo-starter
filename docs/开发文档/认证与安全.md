# 认证与安全

> 本文介绍 monorepo-starter 的认证与安全体系：JWT 双 token、token 撤销、登录失败锁定、全局限流、安全头与 CORS、Turnstile 人机验证。相关代码集中在 `apps/server/src/modules/auth/` 与 `apps/server/src/common/throttler/`。

## 1. 认证流程总览（双 token）

登录成功后由 `TokenIssuanceService.issueTokens` 签发一对 token：

| Token         | 默认 TTL                                | 说明                                                 |
| ------------- | --------------------------------------- | ---------------------------------------------------- |
| access token  | 15 分钟（`JWT_ACCESS_TTL=900`，单位秒） | 请求鉴权用，短期有效，放 `Authorization: Bearer` 头  |
| refresh token | 7 天（常量 `REFRESH_TTL`）              | 刷新 access 用，服务端留存校验，不暴露给前端业务请求 |

JWT payload 结构（`JwtPayload`）：

```ts
{
  sub: (accountId, userType, tokenVersion, jti);
}
```

- `jti`：每次签发随机生成（`randomUUID()`），是黑名单撤销的精确粒度；
- `tokenVersion`：账户级版本号，改密 / 踢人 / 软删时自增，所有旧 token 立即失效（粗粒度兜底）。

刷新流程（`TokenIssuanceService.refreshTokens`）：

1. 校验旧 refresh token 签名与 `jti`；
2. `TokenBlacklistService.isRevoked(jti, accountId)` 检查黑名单（缓存优先，DB 兜底）；
3. 将旧 refresh token 标记为 `used`（写缓存 `auth:refresh:{accountId}:{hash}`，TTL 7 天）；
4. 签发新的一对 token；若检测到已用过的 refresh token 被重用，写入 `TOKEN_REUSED` 审计并撤销该账号全部 token。

## 2. token 撤销：jti 黑名单 + tokenVersion

`TokenBlacklistService` 是撤销中心，两层防护：

1. **`token_revocation` 表（持久化）**：记录精确 `jti` 或 `jti='*'`（账号全量通配）；
2. **`account.tokenVersion`**：粗粒度版本号，旧 token 因 payload 版本不一致而失效。

```ts
// 登出 / 改密 / 软删：撤销账号所有 token
await tokenBlacklist.revokeAccountTokens(accountId, 'logout');
// 精确撤销单个 token（jti）
await tokenBlacklist.revokeToken(jti, accountId, 'manual');
// 快速校验（缓存优先，DB 兜底）
const revoked = await tokenBlacklist.isRevoked(jti, accountId);
```

撤销原因与审计词表共享（`password_reset | password_changed | account_deleted | logout | token_reuse | manual`）。撤销记录由 `CleanupTask` 每日清理（见《定时任务.md》）。

## 3. 登录失败锁定

`LoginLockService` 用缓存计数器实现滑动窗口锁定：

| 维度 | 默认阈值 | 窗口    | 缓存 key                |
| ---- | -------- | ------- | ----------------------- |
| 账号 | 5 次     | 15 分钟 | `auth:lock:{accountId}` |
| IP   | 50 次    | 15 分钟 | `auth:lock:ip:{ip}`     |

阈值优先级（账号维度）：

1. `system_config` 中 `settings.loginFailThreshold`（后台可配，运行时生效）；
2. 环境变量 `LOGIN_LOCK_ACCOUNT_THRESHOLD`；
3. 代码默认值 `5`。

IP 阈值与窗口由 `LOGIN_LOCK_IP_THRESHOLD`（默认 50）与 `LOGIN_LOCK_TTL`（默认 900 秒）控制。锁定触发时写入 `LOGIN_LOCKED` 审计并上报 `login_lockouts_total` 指标；登录成功会清零失败计数。前端可用 `getRemainingAttempts` 返回的剩余次数做提示。

## 4. 全局限流（GqlThrottlerGuard）

`AppModule` 配置 `ThrottlerModule`：**默认 100 次/分钟/IP**，通过 `APP_GUARD` 注册 `GqlThrottlerGuard` 全局生效。

- GraphQL 兼容：守卫重写 `getRequestResponse`，从 `GqlExecutionContext` 取 `req/res`；
- 限流触发时上报 `rate_limit_blocked_total{route,reason}` 指标（route 已归一化，避免高基数）；
- 登录等敏感端点可用 `@Throttle` 单独收紧：

```ts
@Throttle({ default: { limit: 5, ttl: 60_000 } }) // 登录端点：5 次/分钟
@Mutation(() => LoginResult)
login(...) { ... }
```

## 5. 安全头与 CORS 白名单

`createApp()`（`apps/server/src/app-setup.ts`）统一装配：

- `helmet()`：安全响应头（X-Content-Type-Options、CSP 等）；
- `compression()`：响应压缩；`cookieParser()`：cookie 解析；
- `enableCors({ origin })`：CORS 白名单来自 `CORS_ORIGINS`（逗号分隔），默认 `http://localhost:3302`（admin 开发地址）。**生产环境必须显式配置**，不要依赖默认值。

## 6. Turnstile 人机验证

`TurnstileService` 接入 Cloudflare Turnstile（siteverify 端点）：

- 配置来源优先级：`system_config` 的 `turnstile.config`（`enabled` + `secretKey`）→ 环境变量 `TURNSTILE_SECRET_KEY` → 未配置则跳过；
- 校验链：Cloudflare 官方测试密钥快速通道（任何 token 均 success）→ 本地开发 `LOCAL_DEV_BYPASS_` 前缀绕过 → 缓存防重放（token 用后作废，TTL 5 分钟）→ siteverify；
- 前端在登录等场景获取 Turnstile token 后随请求提交，服务端在校验通过后才继续。

## 7. 安全开发 checklist

- 新增接口：默认继承全局限流；敏感操作加 `@Throttle` 收紧 + `@RequirePermission`（见《权限控制.md》）；
- 修改用户凭据 / 踢人：调用 `revokeAccountTokens`，同时写审计（`PASSWORD_CHANGED` / `ACCOUNT_DISABLED` 等）；
- 审计埋点：动作必须 ∈ 词表（见《审计日志.md》），登录失败 / 锁定等安全路径的审计是 fail-open 的，不影响安全判定；
- 环境变量：`JWT_SECRET` 至少 16 字符，生产用密钥管理服务注入，禁止写进镜像；
- 所有安全配置集中在 `apps/server/src/config/env.ts`（zod 校验），改配置后跑 `pnpm typecheck` 与 `pnpm test` 确认。
