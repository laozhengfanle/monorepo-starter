# 定时任务

> 本文介绍基于 `@nestjs/schedule` 的定时任务体系：现有 `CleanupTask` 的职责与调度、以及如何新增定时任务。核心代码：`apps/server/src/common/tasks/`（`tasks.module.ts` / `cleanup.task.ts`）。

## 1. @nestjs/schedule 基础用法

`TasksModule` 引入 `ScheduleModule.forRoot()` 并注册任务类；任务类用 `@Cron` 装饰器声明调度：

```ts
import { Injectable, Logger } from '@nestjs/common';
import { Cron, CronExpression } from '@nestjs/schedule';

@Injectable()
export class MyTask {
  private readonly logger = new Logger(MyTask.name);

  @Cron(CronExpression.EVERY_DAY_AT_3AM, { name: 'my-task' })
  async run(): Promise<void> {
    // 任务体
  }
}
```

- `CronExpression` 提供常用枚举（`EVERY_DAY_AT_3AM`、`EVERY_HOUR` 等），也可传 6 段 cron 表达式字符串（`'0 3 * * *'`）；
- `{ name }` 给任务命名，便于日志与运维识别；
- 任务类与 `TasksModule` 一起注册在 `AppModule`，随应用启动加载。

## 2. CleanupTask：数据清理

`CleanupTask` 是当前唯一的定时任务，**每日凌晨 3 点**执行一次清理：

| 清理项                         | 规则                                                                            | 目的                                     |
| ------------------------------ | ------------------------------------------------------------------------------- | ---------------------------------------- |
| `audit_log`（审计日志）        | 删除 `createdAt` 早于 **90 天**前（`AUDIT_LOG_RETENTION_DAYS = 90`）的记录      | 合规保留窗口内即可，防止无限增长         |
| `token_revocation`（撤销记录） | 删除 `expiresAt` 已过 **7 天**宽限期（`TOKEN_REVOCATION_GRACE_DAYS = 7`）的记录 | 原 token 过期后再留 7 天兜底，无保留价值 |

设计原则（与监控、稳定性强相关）：

- **每个清理动作独立 try/catch**：单个失败不影响整体（如审计表锁住不阻塞黑名单清理）；
- **失败只打日志不抛出**：定时任务绝不能因为异常挂掉主进程；
- 用 Logger 输出清理数量（`已清理 N 条...`），便于运维观察每次清理效果。

## 3. 如何新增定时任务

1. 在 `apps/server/src/common/tasks/` 下新建 `xxx.task.ts`（或业务模块内自建），完整骨架：

```ts
import { Injectable, Logger } from '@nestjs/common';
import { Cron } from '@nestjs/schedule';
import { PrismaService } from '../prisma/prisma.service.js';

@Injectable()
export class ReportTask {
  private readonly logger = new Logger(ReportTask.name);

  constructor(private readonly prisma: PrismaService) {}

  @Cron('0 2 * * *', { name: 'daily-report' }) // 每天 2 点（6 段 cron）
  async generateReport(): Promise<void> {
    try {
      // 业务逻辑（体量大时拆批 + 分页游标）
      const count = await this.prisma.client.someTable.count();
      this.logger.log(`日报生成完成，共 ${count} 条`);
    } catch (err) {
      // 失败只记日志，绝不抛出（定时任务异常不应影响主进程）
      this.logger.error(`日报生成失败: ${err instanceof Error ? err.message : String(err)}`);
    }
  }
}
```

2. 注册：在 `TasksModule` 的 `providers` 数组加入任务类（`ScheduleModule.forRoot()` 已由 `TasksModule` 引入）：

```ts
@Module({
  imports: [ScheduleModule.forRoot()],
  providers: [CleanupTask, ReportTask],
})
export class TasksModule {}
```

3. 任务体遵循三条纪律：**try/catch 兜底、失败只记日志、输出执行摘要**；
4. 补单测（参考 `cleanup.task.spec.ts`：构造 PrismaService 桩，断言 `deleteMany` 收到的 where 条件 / 失败分支不抛出）。

## 4. 测试与观察

- **单测**：桩掉 `PrismaService`，分别断言正常分支（删除数量正确）与失败分支（方法不抛出、日志记录错误）；
- **日志观察**：每次执行输出摘要（如 `已清理 N 条...`），配合 `LOG_LEVEL` 与日志采集可建立"清理是否按时执行"的告警；
- **指标**：如需要可埋点 `BusinessMetrics` 统计执行次数/耗时（见《监控与日志.md》），定时任务无请求上下文，指标是唯一稳定的观测通道。

## 5. 注意事项

- **无请求上下文**：定时任务不在 HTTP 请求链路内，没有 requestId；审计/日志的 `accountId` 应传系统/空（`AuditService.write` 的 `accountId` 可省略）；
- **不要依赖本地时区**：cron 表达式按服务器时区执行，跨时区部署需确认 TTL/窗口语义；
- **幂等与重入**：任务可能因部署重启重复执行，删除/生成类任务应可重入（按条件删除天然幂等）；
- **长任务**：避免单实例重任务阻塞事件循环；耗时可拆批 + 分页游标；
- **与清理相关**：新增会无限增长的实体时，评估是否需要纳入清理策略（保留天数常量 + 独立 try/catch）。
